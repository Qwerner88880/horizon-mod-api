## 1. Коротко

- **Запускать Java-моды внутри Horizon напрямую нельзя.** Это не вопрос времени: Java-моды
  патчат и наследуют тысячи внутренних классов Minecraft, а в Horizon их нет.
- **Выбранный путь:** расширить родной API модов Horizon (WebAssembly-моды на Rust) до
  уровня, которого требуют технические моды, и сделать конвертер, который переносит из
  jar всё, что переносится автоматически, а для остального показывает, каких частей API
  не хватает.
- **Сделано 17 этапов API** (1–6 и 11–17 — на основном ПК, 7–10 — на ноутбуке, я их принял и
  перепроверил, см. §5б), все работают в игре:

  | Этап | Capability | Что даёт моду |
  |---|---|---|
  | 1 | `block-entities` | свои данные на блоках, тик, сохранение с миром |
  | 2 | `energy` | общие для всех модов буферы энергии на блоках, передача соседям |
  | 3 | `menus` | сундучные GUI с кнопками и живым обновлением |
  | 4 | `block-use-events` | правый клик по своим блокам (машины) |
  | 5 | `displays` | модели блоков и текст в мире с плавной анимацией |
  | 6 | `items` | общие для всех модов инвентари на блоках, слоты игрока в меню |
  | 7 | `machine-recipes` | рецепты своих машин из `data/<id>/recipe/`, поиск по входу |
  | 8 | `multiblocks` | шаблоны структур, проверка мира, события «собран/разобран» |
  | 9 | `saved-data` | данные мода на самом мире (сети, точки), сохраняются с миром |
  | 10 | `item-hooks` | предметы с логикой: use, удар, тик, броня, данные на стаке |
  | 11 | `network` | сообщения между серверной и клиентской половиной мода, настоящие экраны |
  | 12 | `entities` | свои мобы мода на ванильном теле: спавн, телепорт, удар, смерть, правый клик |
  | 13 | `fluids` | баки жидкости на block entities (до 8), общие для модов, `push` как труба, вёдра |
  | 14 | `redstone` | чтение сигналов вокруг блоков мода и выдача своих (слабых и сильных) |
  | 15 | `effects` | ванильные частицы и звуки в мире для игроков рядом |
  | 16 | `game-events` | уведомления: урон, смерть, возрождение, смена измерения и режима, убитый моб, погода |
  | 17 | `config` | настройки мода в файле `config/<id>.toml` с комментариями, правка при запущенной игре |

- **Объём:** 35 коммитов в ветке `block-entities-api` репозитория `E:\minecraft_rust\horizon` поверх `f66f66c`
  (26 из них — этапы API, остальные — правки для Windows и сценариев с ноутбука), 74 файла,
  +18 700 / −1 100 строк, уровень API 22, тесты и документация (`docs/mods.md`,
  `docs/api/mods-reference.md`).
- **Отдельная программа `horizon-forge`** (`E:\minecraft_rust\horizon-forge`): находит Horizon,
  ставит в него этапы API (патчами), собирает игру с модами и конвертирует jar.
- **Пример-мод `cells`** проверяет всё вместе: лодстоун становится энергоячейкой, копит и делит
  энергию, открывает меню по правому клику, над ним висит голограмма заряда и крутится сердечник.
  К нему по этапам добавились: бак жидкости, выдача редстоун-сигнала («шкала» заряда), эффекты
  (`/cellfx`), железный голем-«страж» (`/sentinel`), реакции на события игры и файл настроек
  `config/cells.toml` (`/cellconfig`).
- **Что важно знать сразу (подробно — в §14):** всё сделанное работает и проверено
  тестами; в настоящей игре я прогнал каждый этап, но не каждую ветку внутри него. Явно **не
  проверено**: реальный второй клиент по сети, звук на слух, удар посохом и золотой шлем,
  часть типов частиц, сильный редстоун-сигнал, состояние ламп после перезапуска.
  **Не сделано** целиком: серверный контент (блоки из серверного мода), межмодовые вызовы,
  страница настроек в меню, `item_display`, пилотный мод в духе Draconic Evolution.

## 2. Исходная ситуация

### Что такое Horizon

- Около 700 тыс. строк Rust, ~30 крейтов. Главные: `horizon-client` (игра, ~400 тыс. строк),
  `horizon-world` (мир, генерация, блоки), `horizon-mods` (рантайм модов), `horizon-mod-sdk`
  (SDK и WIT-контракт), `horizon-port-pack` (перенос модпаков).
- Почти весь код написан ИИ-агентами, корректность проверяется «харнессами»: тестами,
  которые сравнивают Horizon с настоящим Minecraft 26.3 на одинаковых входных данных.
- Ассетов Mojang в репозитории нет: `horizon-prepare` строит их из твоей лицензионной копии.

### Почему Java-моды не запускаются

Java-мод — это не программа, общающаяся с игрой через узкий API. Это набор классов,
которые:

1. **наследуют классы Minecraft** (`Block`, `BlockEntity`, `Item`, `Entity`, `Screen`,
   `AbstractContainerMenu`...) и переопределяют их методы;
2. **вызывают тысячи внутренних методов** (`Level.setBlock`, `ServerPlayer.openMenu`...);
3. **патчат байткод игры на лету** через Mixin;
4. зависят от модлоадера (NeoForge/Fabric) и библиотек (для DE — BrandonsCore, CodeChickenLib).

В Horizon нет ни одного из этих классов: игра на Rust, «внутренности» другие. Чтобы Java-мод
заработал, нужно было бы поднять JVM и написать на Java полную копию внутреннего Minecraft,
синхронизированную с Rust-миром каждый тик. Это вторая игра поверх первой, медленнее
оригинала. Именно поэтому сам `horizon-port-pack` переносит из модов только данные и ассеты,
а Java-код пропускает.

## 3. Варианты и выбор

| Вариант | Суть | Почему нет / почему да |
|---|---|---|
| **A. JVM внутри Horizon** | загрузить NeoForge и моды в JVM, эмулировать классы MC | Нужна полная копия внутреннего MC на Java с теми же именами (для Mixin) плюс синхронизация с Rust-миром. Объём сопоставим со всем Horizon, производительность хуже ванилы. **Отвергнут.** |
| **B. Автотранспиляция Java→Rust** | перевести байткод мода в Rust | Переведённому коду нечего вызывать: аналогов `Level`, `BlockEntity`, `Menu` нет. Перевод без API бесполезен. **Отвергнут как самостоятельный путь**, но частично входит в D (перевод логики поверх API). |
| **C. Гибрид: Java-сервер + Horizon-клиент** | мод крутится на NeoForge-сервере, Horizon только рисует | Клиенту всё равно нужны реестры, модели, рендер, GUI и сетевые пакеты мода. Без клиентской части мода Horizon покажет лишь ванильное. **Не сейчас**, но идея «протокольного моста» для контентных модов остаётся (см. §10.8). |
| **D. Расширить родной API модов + конвертер** | моды на Rust (WebAssembly) в песочнице; API растёт по этапам до уровня NeoForge; конвертер переносит контент автоматически, а логику переводят поверх API | Опирается на то, что в Horizon уже есть (WASM-рантайм, SDK, контентные моды, `port-pack`). Каждый этап сразу полезен и проверяем. Совместим с апстримом (можно отправлять PR). **Выбран.** |

### Почему WebAssembly-моды, а не, скажем, нативные DLL

- **Песочница:** мод не видит файлы, сеть и процессы, у него лимит памяти и «топлива» (CPU) на
  вызов. Мод может зависнуть или упасть, но игра продолжит работу: мод просто отключится.
- **Один файл `.hmod` для всех ОС и архитектур.**
- **Это уже архитектура Horizon** (wasmtime 48 LTS, component model, WIT-контракт). Мои
  этапы — продолжение его дорожной карты, а не форк с другой философией.
- **Стабильный контракт:** каждая функция API имеет уровень (`api_level.rs`). Мод, которому
  нужен новый уровень, получает понятную ошибку «обновите Horizon», а не падение линковки.

### Почему серверные моды (side = "server")

Логика машин, энергия и инвентари в Minecraft живут на сервере. В Horizon одиночная игра по
умолчанию тоже идёт через серверный поток, а окно — его клиент. Поэтому серверный мод
работает одинаково в одиночке, по LAN и на выделенном сервере. Кроме того, всё, что сервер
показывает игрокам, я делал через **ванильные механизмы** (сундучные меню, display-сущности),
и это видит **любой клиент**, даже ванильный Minecraft, подключившийся к Horizon-серверу.

## 4. Как устроены моды Horizon

(Это было до меня; мои этапы встроены в эту схему.)

```
.hmod (zip) = horizon-mod.toml + mod.wasm (+ assets/ + data/ для контента)

Клиентский мод   api = "0.1", side = "client"  → HUD, чат, свои экраны, рендер HUD, ввод
Контентный мод   api = "0.2", capability registries → блоки, предметы, рецепты, лут (только данные)
Серверный мод    api = "0.3", side = "server"  → команды, тики, игроки, мир (get/set блоков)
```

- **WIT-контракт:** `crates/horizon-mod-sdk/wit/horizon.wit` описывает, что мод импортирует
  (функции игры) и экспортирует (хуки, которые вызывает игра).
- **Capabilities:** каждый импорт требует capability в манифесте. Игрок видит их перед
  включением мода («может: хранить данные на своих блоках...»). Новые и нестабильные
  помечаются `experimental` и требуют явного `experimental = [...]` в манифесте.
- **Рантайм:** `crates/horizon-mods/src/runtime.rs`. Он загружает компоненты, линкует
  хост-функции, вызывает хуки с лимитом топлива и копит `Output` — действия, которые
  игра выполняет после вызова (написать в чат, поставить блоки...).
- **Игра:** `crates/horizon-client/src/game/server_mods.rs` в конце каждого тика отдаёт
  модам события (вход/выход, чат, сломал/поставил блок), «одалживает» им мир
  (`lend_world`) и применяет их `Output`.
- **Песочница для тестов:** `horizon_mods::testing::TestGame` плюс TOML-сценарии
  (`tests/*.toml` у примеров). Мод проверяется без запуска игры.

## 5. Что сделано по этапам

Все этапы — коммиты в ветке `block-entities-api` поверх `f66f66c` (main апстрима). Каждый
коммит несёт строку `Horizon-Forge-Api: <этап>`, по ней `horizon-forge` понимает, что уже
установлено.

### Общий принцип расширения (важно для будущих этапов)

**Новые экспорты — в отдельных host-мирах.** WIT-мир SDK (`horizon-block-mod`) включает всё,
а у игры на каждый новый экспорт свой маленький мир (`block-entity-host`, `menu-host`,
`use-host`, `display-host`), который инстанцируется **опционально**. Так мод, собранный под
старый уровень API, продолжает загружаться: у него просто нет нового экспорта, и игра его не
вызывает. Это повтор приёма, которым Horizon уже добавлял `ui-events`.

**Импорты подтягиваются только при использовании.** wit-component выкидывает неиспользуемые
импорты, поэтому мод, не вызывающий `energy.*`, не требует capability `energy`. (Это
сработало не сразу — см. §8.)

---

### Этап 1 — block entities (`15fd992`, +895 строк)

**Что даёт.** Мод объявляет «свои» блоки (`blocks()`), и на каждой поставленной копии у него
есть байтовые данные (до 16 КиБ, до 65 536 штук на мод). Хуки: `tick` раз в тик со списком
своих block entities в загруженных чанках и `removed`, когда блока не стало (с последними
данными). Импорт: `block-entities.get/set`.

**Как устроено.**
- `horizon-mods/src/block_entities.rs` — хранилище `BlockEntities`: мод → (измерение, позиция)
  → байты. Сохраняется в `<мир>/data/horizon/block_entities.json` через временный файл
  (обрыв записи не портит старый). Битый файл откладывается как `.bad`, а не теряется.
- Хранилище **принадлежит игре** и **одалживается** рантайму на время вызовов (как мир),
  поэтому оно переживает перезагрузку модов.
- Создание: когда игрок ставит заявленный блок (событие `block_placed`) или мод ставит его
  через `world.set-blocks`.
- Удаление: каждый тик для загруженных чанков проверяется, что на позиции всё ещё «свой»
  блок; если нет — `removed` и удаление. Незагруженные чанки не трогаются.

**Почему так, а не через ванильные block entity в NBT чанка.** Ванильный block entity
привязан к *типу* блока, а у модовых блоков (и у ванильных вроде лодстоуна) своего типа нет.
Встраивание в формат чанков задело бы сохранения, совместимость с ванилой и десятки
харнессов. Отдельный файл в `data/horizon/` не трогает ванильные данные мира совсем: мир
открывается ванильным Minecraft как раньше.

**Пример.** `cells`: каждый поставленный лодстоун — ячейка, заряд растёт, `/cell` показывает.

### Этап 2 — энергия (`b3dfae0`, +539 строк)

**Что даёт.** Буфер энергии на своём block entity: `set-storage(ёмкость, max-receive,
max-extract)`, `set-stored`. **Любой мод** может `get/insert/extract` **любой** буфер в его
лимитах (`simulate` — только спросить). `push` раздаёт энергию шести соседям поровну, остаток
ходит по кругу к тем, у кого есть место.

**Почему общая энергия.** В Java-мире это Forge Energy (`IEnergyStorage`). Именно общая
шина позволяет генератору одного мода питать машину другого. Если бы энергия была личными
данными мода (как на этапе 1), моды не могли бы взаимодействовать. Модель «буфер с
лимитами приёма и отдачи за вызов» — та же, что у FE, поэтому перенос Java-логики прямой.

**Как устроено.** `horizon-mods/src/energy.rs` (`Buffers`) живёт внутри хранилища этапа 1
(одалживается вместе с ним), сохраняется в `data/horizon/energy.json`. Владелец буфера — мод
блока; чужой мод может наполнять и забирать, но не менять ёмкость. Буфер удаляется **после**
хука `removed`, чтобы мод успел прочитать, сколько энергии пропало.

**Пример.** Ячейки хранят заряд в буферах, выравнивают его с соседями; старые ячейки
этапа 1 сами переносят заряд из байтовых данных в буфер.

---

### Этап 3 — меню / GUI (`fe5e71f`, +777 строк)

**Что даёт.** `menus.open(игрок, имя, заголовок, ряды 1–6, предметы)`, `set-items`, `close`.
Хуки: `clicked(игрок, меню, слот, кнопка, shift)` и `closed`. `MenuItem::new(...).named(имя, lore)`
в SDK строит предмет с названием и подписью.

**Почему ванильные сундучные меню (как плагинные GUI на Spigot-серверах).**
- Их понимает **любой клиент**, даже ванильный: не нужна клиентская часть мода и сеть
  (сеть — это этап 8, которого ещё нет).
- Всё необходимое уже было в Horizon (окна для торговца и верстака, `open_window`).
- Минус — вид «сундука»: нет своих текстур, полосок и кнопок произвольной формы. Это
  решается позже связкой серверного мода с клиентским UI-модом через сеть (§10.6).

**Как устроено.** Хаб открывает окно `minecraft:generic_9xN`, шлёт содержимое (предметы мода
плюс инвентарь игрока). Клик по такому окну перехватывается **до** всех игровых обработчиков
(`lan_mod_menu_click`), отдаётся моду в конце тика, а содержимое **тут же пересылается
заново**: клиентское «угадывание» перемещения откатывается, и предмет забрать нельзя.
Меню закрывается при выходе игрока (мод получает `closed`).

**Пример.** `/cellgui` (позже и ПКМ по ячейке): заряд с полоской, «Drain», «Fill», «Close»,
обновление дважды в секунду.

### Этап 4 — свои блоки, правый клик (`a43b219`, +308 строк)

**Что даёт.** Экспорт `block-use-events`: `uses()` — какие из заявленных блоков мод
«забирает», `used(игрок, блок)` — клик с данными блока. Клик по такому блоку больше ничего
не делает в игре (ни ванильного действия, ни установки блока вплотную). **Shift + ПКМ с
предметом** работает как в ванилле, чтобы можно было строить у машин.

**Как устроено.** Хук стоит в начале `use_hand` (`game.rs`), общего для локального игрока и
гостей сервера: решение «забрать клик» принимается **синхронно** по списку блоков, а сам
вызов мода — **в конце тика** вместе с остальными событиями.

**Почему вызов отложен.** Внутри обработки клика гостя мир и хаб «вынуты» из игры, а мод
хочет открыть меню, тронуть энергию, узнать игроков. В конце тика всё это корректно
одолжено. Задержка — не больше одного тика (50 мс).

**Свои блоки как таковые.** Новые блоки с моделями и текстурами приносит **контентный мод**
(API 0.2), например тот, что делает `horizon-forge convert` из jar. Серверный мод их
«присваивает» (`blocks()` + `uses()`). Поэтому машина = контентный мод (вид) + серверный
мод (логика). Склейка в один `.hmod` — задача на будущее (§10.3).

### Этап 5 — рендер / дисплеи (`4712955`, +570 строк)

**Что даёт.** `displays.show(имя, измерение, x, y, z, форма, трансформ, интерполяция)` и
`hide(имя)`. Форма — модель **любого блока** или **текст** (повёрнут к смотрящему).
Трансформ: сдвиг, масштаб, поворот (кватернион); клиент **плавно** переходит к новому за
заданное число тиков. В SDK: `Transform::identity().scaled(..).turned_y(..).translated(..)`.

**Что выяснилось.** Сервер Horizon принимал `/summon minecraft:block_display`, но такие
сущности не доходили до клиента, а клиент Horizon вообще не рисовал `block_display` (только
`text_display`). Поэтому этап — это и сервер, и клиент:

- **Сервер:** дисплеи мода живут в игре как «виртуальные» сущности — только пакеты
  `AddEntity` + `SetEntityData` (+ `RemoveEntities`), в мир не записываются. Игроки своего
  измерения получают их сразу, вновь пришедшие — при следующей синхронизации. При смене
  только трансформа/текста шлются лишь метаданные (клиент интерполирует). Дисплеи
  выключенного мода убираются.
- **Клиент:** `block_display` рисуется через `block_model_vertices` (тот же путь, что у
  падающих блоков) с матрицей дисплея `T·L·S·R` и интерполяцией, уже реализованными для
  текстовых дисплеев.

**Почему display-сущности.** Это ванильный механизм современных Minecraft-плагинов для
«своего рендера» без клиентских модов: голограммы, анимированные модели из блоков, лучи.
Работает и в ванильном клиенте. Свой 3D-рендер «с нуля» потребовал бы клиентской части мода
и сети.

**Пример.** Над каждой ячейкой парит заряд («94011 FE»), под ним вращается сердечник из
блока редстоуна вокруг своей оси (сдвиг пересчитывается под поворот, проверено тестом).

### Этап 6 — инвентари и слоты (`3964813`)

**Что даёт.** `items.set-slots` даёт своему block entity до 54 слотов; `get`, `insert`
(сначала на одинаковые стаки, потом в пустые) и `extract` работают с **любым** инвентарём,
`set` — со своим. Стек = предмет + количество + компоненты в ванильном синтаксисе.
`menus.open-inventory` открывает меню, часть слотов которого показывает инвентарь блока в
режиме `Storage` (как сундук), `Input` (только положить: вход машины, топливо) или
`Output` (только забрать: выход машины).

**Почему общие инвентари.** Тот же довод, что с энергией: это аналог `IItemHandler`
NeoForge — трубы одного мода кормят машины другого. Модель «слоты + insert/extract с
simulate» совпадает с Java-API, перенос логики машин прямой.

**Как устроено.**
- `horizon-mods/src/items.rs` (`Inventories`) живёт рядом с энергией в хранилище block
  entities, сохраняется в `data/horizon/items.json`. Размер стака берётся из таблицы
  предметов игры (одалживается вместе с миром), неизвестный предмет не вставляется.
- Когда блок пропадает, предметы инвентаря **выпадают на землю** (после `removed`); при
  уменьшении числа слотов выпадает лишнее. В игре это `pop_resource`, как у ванильных
  контейнеров; выпадение в «припаркованном» измерении ждёт, пока оно будет тикать.
- Клики по привязанным слотам обрабатывает хаб (`mod_menu_click` в `lan/containers.rs`):
  левый клик — весь стек, правый — половина или один, обмен разными предметами, Shift —
  перенос между инвентарём блока и игрока (в конец хотбара, как в ванилле). `Output`-слот
  при клике с тем же предметом в руке добавляет в руку (как слот результата верстака).
  После клика сервер шлёт точное состояние — клиентские догадки откатываются.
- Меню **следит за инвентарём**: если мод изменил слоты (машина сделала выход), открытое
  меню обновляется в тот же тик.

**Почему своя логика кликов, а не ванильный движок контейнеров Horizon.** Тот движок
жёстко привязан к ванильным block entity мира (`Slots::Block`) и синхронизации чанков;
встраивание туда стороннего хранилища задело бы много ванильного кода и харнессов. Свой
набор из pickup/shift покрывает реальное использование, а остальное (драг, цифры)
безопасно откатывается.

**Пример.** У ячейки два слота: положил пыль редстоуна во входной — ячейка «съедает» её по
одной (+1000 FE, если есть место); кнопка Drain делает из 1000 FE пыль в выходном слоте,
откуда её можно только забрать. Проверено в игре: Drain×3 → 3 пыли; положить в выход
нельзя; во вход — 8 штук, сразу съедена 1; Shift-клик выхода → в хотбар; ломание ячейки
выбросило 5 пыли на землю.

### Этап 7 — рецепт-типы машин (`machine-recipes`, уровень API 13)

Рецепты **своих** машин: файлы `data/<id>/recipe/**.json` внутри `.hmod` (и в папке мода),
тип рецепта произвольный (`cells:grinding`). Читает `horizon-mods/src/machine_recipes.rs`:
формы ингредиентов ванили, псевдонимы полей (`input/ingredient`, `result/output`), теги
через замыкание игры, битые файлы пропускаются, дубликаты по id (пакет мода бьёт
перенесённый контент), лимиты 16 КиБ на файл и 512 рецептов на мод. API: `all()` и
`by_input(...)` (до 64 ответов). Игра подаёт таблицу тегов (`game/machine_recipes.rs`) **до**
`init` мода, поэтому мод видит рецепты уже при запуске. Пример: помол
булыжника/андезита в редстоун, `/cellrecipes`, кнопка «Load cobble».
**Зачем:** конвертер уже переносит рецепты Java-мода (`recipe/*.json`) — теперь у машины
есть что искать по входу; это закрывает «recipe type» из таблицы соответствий.

### Этап 8 — мультиблоки (`multiblocks`, уровень API 14)

Шаблоны `data/<id>/multiblock/*.json`: палитра, слои, якорь, `air`/`any`; лимиты 64 /
4096 блоков и др. Проверка (`check`) по id блока с поворотом на четверти оборота.
Мод может **следить** за структурой (`watch`): игра сама проверяет её раз в 20 тиков
(бюджет 8192 чтений за проход) и шлёт события `multiblock_formed` / `multiblock_broken`
(с последними данными block entity). Список наблюдаемых сохраняется с миром.
Пример: кольцо из железа 3×3×3 вокруг ячейки — «ядро», заряд ×10, `/cellcore` называет
первый недостающий блок. **Зачем:** энергоядро и fusion-крафт Draconic Evolution — это
мультиблоки.

### Этап 9 — мировые данные (`saved-data`, уровень API 15)

`saved_data::get/set/delete/keys`: байты по ключу на **самом мире**, а не на блоке (лимиты
64 КиБ на значение, 256 ключей, 1 МиБ на мод), файл `data/horizon/saved_data.json`; битый
файл откладывается как `.bad` и не роняет остальное хранилище. Пример: сети питания
`/cellnet <имя>` — ячейка вступает в сеть, перезапуск мода ничего не теряет, сеть исчезает
с последней ячейкой. **Зачем:** сети энергии, владельцы, точки телепорта — всё, что
не привязано к одному блоку.

### Этап 10 — предметы с логикой (`item-hooks`, уровень API 16)

Мод «присваивает» предметы по id (`minecraft:blaze_rod` или предмет контентного мода) и
получает: `item_used` / `item_used_on_block` (ПКМ, в конце тика; sneaking, вторая рука и
блоки, чьё использование забрал мод, остаются ванильными), `hurt_entity` (удар: мод
отвечает, сколько урона нанести, 0 — отменить, до ×4 ванили), `inventory_tick` (все
заявленные стаки игроков, в руке и надетые, до 512 за вызов, остальные по кругу),
`player_hurt` (броня: сколько урона поглощает мод — падение, фейерверк, магия/яд,
жемчуг, дракон, молния, шипы) и **данные на стаке** (`item_hooks::stack/set_data`, до 4 КиБ,
41 слот). Данные хранятся **компонентом самого стака**, поэтому едут с ним между слотами,
игроками и сохранениями без отдельного файла; стак с данными всегда в единственном
экземпляре (иначе разделение удвоило бы заряд).
Пример: энергетический посох (блейз-род) и золотой шлем-щит. **Зачем:** это вся «броня и
инструменты со щитами и зарядом» Draconic Evolution. Не сделано: левая рука, ломание блоков

## 5в. Этап 11 — сеть и настоящие экраны (`network`, уровень API 17)

**Задача.** До сих пор GUI был только сундучным меню: его понимает любой клиент, но у него
нет своей вёрстки. Чтобы получить настоящий экран, нужна клиентская половина мода и
канал между ней и серверной.

**Как устроено.**
- **Две половины одного мода с общим id.** Серверный мод (`side = "server"`) и клиентский
  (`side = "client"`) лежат двумя файлами и носят один id (`cells`). Включение id в
  Options → Mods включает обе; каждая запускается там, где ей положено (клиентская — в игре
  игрока, серверная — где живёт мир). В одиночной игре окно — клиент своего же сервера, так
  что схема одна и та же для одиночной, LAN и выделенного сервера.
- **Транспорт.** Один канал пользовательских пакетов `horizon:mod_net` в состоянии play
  (`horizon-protocol/src/mod_net.rs`): id мода, имя канала мода, байты. Лимиты: имя
  `[a-z0-9_./-]{1,64}`, до 30 000 байт, 64 сообщения и 256 КиБ за вызов, 32 сообщения в тик
  от игрока. Сервер **объявляет** канал в фазе configuration (как это уже делали «тихие
  команды»); Horizon-клиент после этого шлёт сообщения, а сервер шлёт только клиентам с
  брендом `horizon`. Ванильные клиенты и серверы его не видят.
- **API.** Сервер: `network::send_to(player, channel, bytes)` и хук `client_message(player,
  channel, bytes)`; клиент: `network::send(channel, bytes)` и хук `network_received(channel,
  bytes)`. Одна capability `network` для обеих сторон (манифест теперь различает «для обеих
  сторон»: `Capability::both_sides`).
- **Экран.** Клиентская половина по сообщению открывает экран обычными виджетами `ui`
  (текст, кнопка, строка с предметом); повторный `open_screen` заменяет экран, так что
  обновление — это тот же вызов с новыми числами. Нажатие кнопки приходит как `ui_select`,
  клиент шлёт его серверу, **сервер решает**, что оно делает, и присылает новое состояние.
- **Пример.** `/cellui` открывает экран ячейки: заряд числом, шкала `[|||....]`, строка с
  редстоуном, кнопки Fill и Drain; сервер шлёт состояние каждые 10 тиков, пока экран
  открыт, и закрывает его, если ячейку сломали. Клиентская половина — новый пример
  `crates/horizon-mod-sdk/examples/cells-ui`.

**Почему так, а не иначе.**
- *Общий id вместо поля «серверная половина» в манифесте:* ничего нового в манифесте, как у
  модов NeoForge (один id на обеих сторонах); сообщение и так указывает id адресата.
- *Один канал на все моды, а не канал на мод:* канал нужно объявлять в configuration до
  того, как моды загружены, а набор модов может меняться; один канал и id внутри пакета
  не требуют регистрации.
- *Виджеты `ui`, а не новый тип «шкала»:* добавление варианта в `widget` могло бы сломать
  контракт существующих клиентских модов (типы компонентов сверяются структурно). Шкала
  собрана из текста.
- *Серверу нельзя верить клиенту:* пример хранит на сервере «какую ячейку я показал этому
  игроку» и игнорирует любые координаты в сообщении; тест проверяет, что игрок, которому
  ничего не показывали, не может заставить сервер действовать.

**Что нашлось по пути.** Цвет текстовых виджетов мода рисовался с перепутанными красным и
синим (документировано `0xRRGGBB`, а рисовалось как ABGR): оранжевый превращался в синий. Все
существующие моды используют белый, так что поправил одну строку. Тестовый «фиктивный»
компонент в песочнице строится из всего мира `horizon-ui-mod`, поэтому его манифест
пришлось дополнить `network`.

**Проверено.** Юнит-тесты кодека (`mod_net`: круг туда-обратно, лимиты, мусор), 2 новых
сценария (`cells/tests/network.toml`: открыть, fill, drain, мусор, чужой канал, игрок без
экрана, периодическое состояние, закрытие, разрушение ячейки; `cells-ui/tests/screen.toml`:
экран из сообщения, обновление, кнопки, мусорное состояние, закрытие), в песочнице новые
шаги `net`, `select`, `ui-close` и проверки `expect.net`, `expect.screen`. **В настоящей
игре:** `/cellui` открыл экран, кнопки Fill и Drain дошли до сервера и обратно, числа
обновляются сами, «Done» закрывает экран, повторное открытие работает, разрушение ячейки
закрывает экран, ошибок в логе нет; скриншоты сняты.

**Не проверено и не сделано.** Реальный второй клиент по сети (выделенный сервер + чужой
клиент): путь тот же, что у одиночной игры, но по TCP я его не гонял. Сервер не знает, есть
ли у клиента клиентская половина мода (экран просто не откроется; запасной вариант —
сундучное `/cellgui`). Нет свободной вёрстки, текстур и ползунков.

## 5г. Этап 12 — свои мобы мода (`entities`, уровень API 18)

**Задача.** Для Chaos Guardian, дронов, стражей и т. п. моду нужны существа, которых он
сам создаёт, двигает, бьёт и убирает. Писать для них отдельную модель сущности в движке
Horizon нельзя (модель — это данные клиента, а не сервера), поэтому выбран путь:

**Как устроено.**
- **Мод спавнит ванильного моба и помечает его.** `entities::spawn(dimension, x, y, z,
  options)` берёт любой вид моба, который знает игра (`minecraft:iron_golem`), тег мода
  (`sentinel`) и флаги: `no_ai` (мод двигает сам), `invisible` (тело скрыто, поверх него
  ставят display-модели из этапа 5), `silent`, `invulnerable`, `no_gravity`, `takes_use`,
  имя и здоровье. Возвращает id сразу. Так моб получает всё ванильное: хитбокс, физику,
  урон, откидывание, лут, сохранение, сетевую синхронизацию.
- **Метки в сохранении.** Игра находит мобов мода по записям в их `Tags`
  (`horizon_mod:<id>`, `horizon_tag:<tag>`, `horizon_use`): они сохраняются с миром, и
  после перезапуска мод снова слышит своих мобов (проверено в игре). Хранилище в модуле
  для этого не нужно.
- **Управление.** `get`, `list`, `teleport`, `push`, `set_health`, `remove` — только для
  своих мобов; чужие — ошибка. Лимиты: 1024 моба на мод, 32 спавна за вызов, 512 мобов в
  `entity_tick`.
- **События.** `entity_tick` каждый тик; `entity_hurt(player, mob, damage)` — удар
  **игрока** перед тем, как он ляжет (мод отвечает, сколько урона нанести: 0 отменяет, не
  больше 4×); `entity_died` один раз; `entity_removed` с последним состоянием;
  `entity_used` — правый клик по мобу с `takes_use` (клик больше ничего не делает; с
  Shift остаётся ванильное поведение).
- **Почему спавн нельзя в `entity_hurt`.** Id для спавна резервируется заранее (счётчик
  игры + 1), а игра применяет спавн сразу после вызова; в хуках посреди тика (удар, хуки
  предметов) это небезопасно, поэтому там спавн честно возвращает ошибку. Команды, тики,
  входы, клики по меню и блокам спавнить могут.
- **Смерть и исчезновение находятся сканированием** мобов раз в тик (по меткам), а не
  хуком в каждом месте смерти: так ловится любая причина смерти и любое исчезновение.

**Игровой мост.** `game/server_mods.rs`: `ModEntityBook` (какие мобы чьи, что им последний
раз сообщали), `scan_mod_entities`, `lend_mod_entities`/`return_mod_entities` (заём мобов
на время вызовов, как с block entities), `apply_entity_output`, `mod_entity_hurt` (вызывается
из `attack_mob`), `mod_entity_use` (из `interact_mob`).

**Пример.** `/sentinel` в `cells`: железный голем с именем; получает треть урона от удара,
лечится на 1 в секунду, на правый клик отвечает здоровьем, при смерти сообщает серверу.
Шаги песочницы: `strike`, `interact`, проверки `expect.entities`, `expect.dealt`.

**Найденная по пути ошибка (исправлена).** Пока обрабатывается пакет гостя (а в обычной
одиночной игре окно — именно гость своего сервера), узел гостей изъят из игры, и
`acting_server_player` не находил игрока. Из-за этого **ответ предметов на удар (посох
из этапа 10) в одиночной игре не доходил до мода**: в юнит-тестах это не видно. Теперь
действующий игрок собирается из состояния самой игры. Проверено живым ударом по
стражу; удар посохом вручную я по-прежнему не мерил.

**Проверено.** 56 юнит-тестов `horizon-mods`, 32 теста песочницы (новый сценарий
`cells/tests/entities.toml`: спавн, удар 6 → 2, лечение, правый клик, смертельный удар,
сообщение о смерти, исчезновение тела), clippy без предупреждений, fast-сборка. **В
настоящей игре:** `/sentinel` спавнит голема (id сразу), удар незеритовым мечом даёт 8 →
2,67 урона, правый клик отвечает здоровьем (после исправления — один раз, а не за обе
руки), `/kill` даёт «A sentinel fell», после сохранения и перезапуска страж найден снова.

**Не сделано.** Урон не от игрока (огонь, падение, другие мобы) не доходит до
`entity_hurt`; мобы только в измерении, которое симулирует сервер; нет своих целей ИИ (мод
двигает моба `teleport`/`push` каждый тик); нет мобов не-ванильных видов (своя модель —
через display-сущности); позицию display-моделей за двигающимся мобом пока приходится
пересоздавать (плавного `teleport_duration` нет); реальный второй клиент по TCP не гонял.

## 5д. Этап 13 — жидкости (`fluids`, уровень API 19)

**Задача.** Баки, трубы, насосы: то, что у Forge называется fluid handler. Нужно, чтобы
жидкость в блоке одного мода принимал и отдавал другой, как уже сделано для энергии и
предметов.

**Как устроено.** По образцу энергии, в том же хранилище, что block entities.
- **Баки на block entity.** `fluids::set_tanks` даёт своему block entity от 1 до 8 баков
  (ёмкость до 2^50 мБ, максимум входа и выхода за вызов). Бак держит **одну жидкость за
  раз**, имя `namespace:path` — ванильная (`minecraft:water`) или своя (`cells:plasma`).
  Реестра чужих жидкостей у игры нет, поэтому проверяется только форма имени. Количества в
  миллибакетах (ведро = 1000).
- **Общие для модов.** `get`, `insert`, `extract` работают с баками любого мода. `insert`
  сначала льёт в бак, где уже эта жидкость, потом в пустой, и никогда не смешивает.
  `extract` называет бак и возвращает жидкость с количеством. `simulate` только говорит,
  сколько пройдёт.
- **`push` — труба.** Переливает из своего бака в баки на шести сторонах, которые берут
  эту жидкость, поровну; что один не взял, идёт кругу остальным (тот же алгоритм, что у
  энергии).
- **Вёдра.** `fluid_of_bucket` и `bucket_of_fluid` для ванильных вёдер (вода, лава, снежная
  пыль). Само наполнение ведра — работа `items`/`item-hooks`.
- **Жидкости мира.** Отдельных вызовов нет: насос читает блок через `world` (`water[level=0]`
  — источник), убирает его `set-blocks` и делает `insert`.
- **Жизнь.** Баки лежат в `BlockEntities.fluids`, сохраняются в `data/horizon/fluids.json`,
  удаляются вместе со своим block entity (после `removed`, который ещё может их читать).
  Ничего нового в игровой части не потребовалось: хранилище уже занимается
  сохранением и одалживанием.

**Пример.** У каждой ячейки `cells` теперь бак на 16 вёдер. Ячейка оставляет себе пол-ведра
и отдаёт остальное по 100 мБ за тик соседним ячейкам, поэтому налитая жидкость растекается и
успокаивается. Команда `/cellfluid [water|lava|drain|read] [pos]`.

**Проверено.** 6 юнит-тестов хранилища (лимиты, нет смешивания, несколько баков, владелец,
`push` с отказом стороны с другой жидкостью, вёдра и имена, сохранение), новый сценарий
`cells/tests/fluids.toml` (налить, растечься до 500/500, лава не смешивается, слить с
названием ведра, пустой бак, нет ячейки), все 62 юнит-теста и 32 теста песочницы, clippy
без предупреждений. **В настоящей игре:** две соседние ячейки, налил 1000 мБ воды в одну —
через несколько секунд 500/500; лава отклонена; слив вернул «500 мБ воды (water_bucket)»;
`fluids.json` записан; после сохранения и перезапуска содержимое на месте.

**Не сделано.** Жидкости в предметах (баки на стаках, ведро с жидкостью мода), ванильные
воронки и трубы не видят баки, жидкие блоки своей жидкости (контентный мод пока не
объявляет жидкость), показ бака в меню шкалой. Поведение «труба» — это `push`, который мод
вызывает сам каждый тик; встроенной сети труб нет.

## 5е. Этап 14 — редстоун (`redstone`, уровень API 20)

**Задача.** Машины и датчики мода должны жить в одной схеме с ванильным редстоуном: ловить
сигнал от рычага и провода и подавать свой лампам, поршням, повторителям.

**Единственный этап, который тронул движок мира.** Блок мода — обычный ванильный блок
(лодстоун), а ванильные блоки читают сигналы по состоянию блока, поэтому нужен был крючок в
самом движке:
- `horizon-world`: `LevelAccess::mod_signal(pos, side, strong)` (по умолчанию 0), который
  опрашивают `state_signal` и `state_direct_signal` — те же функции, через которые лампы,
  провод, повторители и двери читают `getSignal`/`getDirectSignal`. Плюс
  `Behaviours::neighbor_signals(level, ticks, pos)` — шесть сигналов, которые блок получает от
  соседей.
- Игра: карта «источники текущего измерения» (`Game::mod_emitters`), которую читает вид
  уровня (`with_level`). Сохранённое состояние хранится в `BlockEntities.redstone`
  (`data/horizon/redstone.json`), поэтому сигнал стоит после перезапуска ещё до того, как мод
  отработает.

**Как это видит мод.**
- **Чтение.** Игра раз в тик считает сигнал на каждой из шести граней каждого block entity мода
  и кладёт его в заём хранилища (`redstone.inputs`). Мод слышит `redstone_changed(измерение,
  x, y, z, input)` при изменении, при первом чтении (блок поставили, мир или мод
  запустились — опрашивать не нужно) и при изменении соседнего блока, не больше 256 за тик;
  `redstone::get_input` читает то же в любой момент. Читать можно только свои блоки.
- **Выдача.** `redstone::set_output(.., RedstoneOutput { power, strong })`: сила 0–15 на каждой
  грани. `weak` — как у блока редстоуна, `strong` — как у рычага (питает блоки насквозь).
  Окружающие блоки обновляются как при рычаге (при сильном — и соседи соседей). Выход
  чужого блока доступен только на чтение (`get_output`).
- **Почему входы считает игра заранее, а не мод по запросу.** Мод вызывается с «одолженным»
  миром (чанки забраны у игры), а вычислять сигнал нужно движком `Sim` над настоящим уровнем.
  Поэтому игра считает сигналы перед вызовами и кладёт результат в хранилище.

**Пример.** Ячейка `cells` выдаёт «шкалу» заряда (уровень на каждые 1000 FE) на все грани и
перестаёт заряжаться, пока на её верхнюю грань приходит сигнал. (Сначала я сделал «любая
грань» — две соседние ячейки заперли друг друга своими шкалами; ловил это в игре. Теперь
только верх.)

**Проверено.** 4 юнит-теста хранилища, сценарий `cells/tests/redstone.toml` (первый тик без
сигнала, налили 1000 FE — уровень 1, сигнал сверху остановил заряд, снятие возобновило, блок
сломали — сигнал ушёл), в песочнице шаги `signals` и проверка `expect.redstone`; 66 юнит-тестов
`horizon-mods`, 32 теста песочницы, 59 тестов уровня `horizon-world`, clippy без
предупреждений. **В настоящей игре:** редстоуновая лампа рядом с ячейкой загорелась, блок
редстоуна сверху вдвое снизил суммарную скорость зарядки (1178 → 2355 FE за 10 с после
снятия), `redstone.json` записан.

**Не проверено и не сделано.** Состояние ламп после перезапуска мира не проверял отдельно
(файл записан, но сам перезапуск с проверкой лампы я не делал). Сильный сигнал
(`strong: true`) проверен только в юнит-тестах хранилища, но не в игре. Провод и повторители
визуально не подключаются к блоку мода (блок редстоуна подключается), компараторы не читают
инвентарь мода, нет quasi-connectivity, мобы (поиск пути) сигнал мода не видят; работает
только измерение, которое симулирует сервер.

## 5ж. Этап 15 — частицы и звуки (`effects`, уровень API 21)

**Задача.** Машины и оружие мода должны искрить, дымить, звенеть: без этого мир с модом
«немой». Игрок должен получать это и на клиенте Horizon, и на ванильном.

**Как устроено.** Мод ничего не рисует и не играет сам: он просит сервер, а сервер шлёт
игрокам обычные пакеты игры (`LevelParticles`, `Sound`) через тот же хаб, что и остальной
сетевой код, — поэтому одиночная игра (окно — гость своего сервера), LAN и ванильные клиенты
получают одно и то же.
- **Частицы.** `effects::spawn_particle(dimension, Particle)`: имя (любая ванильная частица),
  точка, разброс по осям (0–64), скорость (0–10), количество (до 500). Частицы, которым нужны
  данные, берут их из `color` и `scale` (dust, dust_color_transition, entity_effect, effect,
  instant_effect, tinted_leaves) или `block` (block, block_marker, falling_dust, dust_pillar,
  block_crumble). Игроки в 32 блоках получают её (`always_show` — в 512). Предметные частицы,
  trail, vibration и flash не отправляются: у них данные, которые нельзя собрать из этих полей
  (для flash сетевая форма в игре не собирает цвет). Неизвестная или без нужных данных —
  отбрасывается и пишется в лог.
- **Звуки.** `play_sound(dimension, sound, x, y, z, volume, pitch, category)` — в мире
  (громкость 0–10, слышно на 16 блоков за единицу, высота 0.5–2); `play_sound_to(player, ..)`
  — одному игроку у него же (сигнал). Категория — ползунок громкости, на котором звук играет
  (`master`, `music`, `record`, `weather`, `block`, `hostile`, `neutral`, `player`,
  `ambient`, `voice`). Звук, которого игра не знает, уходит по имени и играет, если он есть в
  ресурспаке игрока.
- **Лимит.** 128 эффектов за вызов хука; только измерение, которое симулирует сервер.
- **Проверка данных в хосте.** Формы имён, диапазоны, конечность чисел; всё остальное (есть
  ли такая частица, существует ли блок) знает только игра, поэтому там остаётся «отбросить и
  записать в лог».

**Пример.** `/cellfx` в `cells`: пыль над ячейкой (зелёная, когда шкала больше половины,
красная до того) и звон, высота которого растёт со шкалой; гибель стража теперь дымит
(`large_smoke`) и звучит голосом голема.

**Проверено.** Сценарий `cells/tests/effects.toml` (уровень 0 и 1, ничего без запроса,
ошибка без ячейки) и добавленная проверка в `entities.toml`, новая проверка `expect.effects`
в песочнице; 66 юнит-тестов и 32 теста песочницы, clippy без предупреждений. **В настоящей
игре:** `/cellfx` увеличил число частиц `dust` на окне на 20, счётчик услышанных звуков
`block.note_block.chime` вырос; гибель стража дала 20 `large_smoke` и звук
`entity.iron_golem.death`. Звук слышать ушами я не мог (в игре выключен аудиовывод), поэтому
проверка — по счётчику услышанных звуков клиента.

**Не сделано.** Собственные звуки мода (файлы и `sounds.json` контентного мода сюда не
подключены, не проверено), звуки, следующие за сущностью, остановка уже играющего звука,
частицы с предметами, trail и vibration, эффекты в других измерениях. Цветные частицы
проверены только на `dust` и `large_smoke` в игре; остальные типы данных (`block` и др.)
проверены лишь тем, что код собирается, а в игре не гонялись.

## 5з. Этап 16 — события игры (`game-events`)

**Задача.** Шина событий в духе NeoForge: мод хочет знать, что игрока ранили, он умер,
перешёл в другое измерение, что моб убит, что погода сменилась — без опроса.

**Как устроено.** Это уведомления постфактум, а не перехваты: если моду нужно изменить
исход, он использует хук той возможности, которой исход принадлежит (`item-hooks`: урон по
броне; `entities`: урон по мобам мода). Чтобы не вешать крючки на десятки мест игры,
большую часть событий находят **сравнением состояния за тик** (одно место в
`tick_server_mods`):
- здоровье, измерение и режим игры каждого игрока сравниваются с прошлым тиком — отсюда
  `player_damaged` (сколько потеряно, до скольки), `player_respawned`, `dimension_changed`,
  `game_mode_changed`; работает одинаково для игрока окна, гостей LAN и игроков
  выделенного сервера;
- `weather_changed` — смена `raining`/`thundering` мира (`clear`, `rain`, `thunder`);
- два события берутся из настоящих путей игры, потому что состояния для них недостаточно:
  `player_died(player, cause)` — игра пишет сообщение о смерти (`was slain by Zombie`) и
  отдаёт его тексту (и для гостя, и для игрока окна); `mob_killed(player, kind, id)` — после
  ближнего удара в `attack_mob`, если моб умер.
- Мод реализует только нужные ему методы `ServerMod`; без экспорта работает как раньше. Новых
  вызываемых функций нет, поэтому **уровень API не растёт** (оставил 21).

**Пример.** `cells`: сообщает о смерти, смене измерения, убитом мобе (со счётчиком игрока) и
смене погоды. Шаг песочницы `game-events = [...]`.

**Проверено.** Сценарий `cells/tests/game-events.toml`; 66 юнит-тестов и 32 теста
песочницы, clippy без предупреждений. **В настоящей игре:** `/weather rain` и `clear` дали
«The weather turns to …»; зомби убит мечом — «You felled a minecraft:zombie (1 so far)»; вход
в Незер — «Welcome to minecraft:the_nether»; `/kill @s` — «Player28692 died: Player28692 was
killed».

**Не проверено и не сделано.** `player_damaged` и `player_respawned` в игре я не наблюдал (мод
на них ничего не печатает; они проверены только сценарием). Нет источника и атакующего
урона, убийств дальним оружием и взрывами, спавнов мобов, подбора и выброса предметов,
достижений, команд игроков и **отменяемых** событий (для блоков, чата и предметов есть свои
хуки). Урон за тик сливается в одну потерю.

## 5и. Этап 17 — конфиги (`config`, уровень API 22)

**Задача.** Настройки мода (скорость зарядки, множители, звуки) должны лежать там, где их
правит игрок или администратор, с описаниями и границами — как `config/*.toml` у Forge, а не в
двоичном `storage`.

**Как устроено.**
- **Схема в коде мода.** `config::declare(&[ConfigEntry...])` в `init`: ключ
  (`[a-z0-9_.-]{1,64}`), описание, вид и значение по умолчанию. Виды: флаг, целое и число в
  пределах `min..=max`, текст, выбор из списка (1–32 варианта). До 128 записей. Хост
  проверяет схему (умолчание в пределах, пустой выбор, повтор ключа — ошибка).
- **Файл `config/<id>.toml`** рядом с файлом мода (в `horizon-mods/`). При первом `declare`
  пишется целиком: над каждой записью описание и строка «1 to 1000. Default: 5». Файл читается
  раз в 5 секунд (`config_tick`), игрок может править при запущенной игре.
- **Правила чтения.** Значение, которого нет, не того вида или вне пределов, — умолчание,
  файл переписывается с исправлением, причина идёт в лог. Целое принимается там, где ждут число.
  Файл, который не разбирается как TOML, **не трогается** (мод держит прежние значения, лог
  один раз). Файл со всеми верными записями не переписывается — комментарии игрока целы;
  при переписывании (недостающая или неверная запись) они теряются.
- **Мод узнаёт.** `ServerMod::config_changed(keys)` — какие записи изменила правка файла (в
  порядке схемы); о собственном `config::set` мод не уведомляется. Чтение — обычный вызов
  `config::get` (удобные `config_integer/number/flag/text` с запасным значением).
- **`config::set`** проверяет и пишет файл — для команды или экрана самого мода (не больше 16
  записей за вызов).
- **Логика отделена от wasm:** модуль `horizon-mods/src/config.rs` (схема, чтение, запись,
  проверка) не знает про рантайм и покрыт юнит-тестами.

**Пример.** `cells` читает из файла заряд за тик, множитель ядра, делитель урона стража, имя
стража, звук `/cellfx` и объявление смертей; команда `/cellconfig [ключ] [значение]`.

**Проверено.** 7 юнит-тестов `config.rs` (значения по умолчанию, правка, неверное значение,
целое как число, непарсящийся файл, новая запись в файле игрока, проверка `set`, отказ схем);

## 6. horizon-forge

`E:\minecraft_rust\horizon-forge` — отдельная программа на Rust (≈630 строк, одна зависимость
`serde_json`). Интерфейс на русском.

| Команда | Что делает |
|---|---|
| `find` | ищет исходники Horizon (`HORIZON_SRC`, текущая папка, домашняя, диски на 2 уровня) и пишет, стоит ли API |
| `install-api [--src] [--release \| --no-build]` | в ветку `horizon-forge-api` накладывает **недостающие** патчи (`git am --3way`), затем собирает игру с модами (профиль `fast`, или `release`) |
| `convert мод.jar [--out] [--install]` | через `horizon-port-pack check` переносит ассеты и данные, читает классы, пишет `api-report.md` (особенности кода → этап API → статус), с `--install` кладёт в `horizon-mods/` |

**Как устроен install-api.**
- Патчи вшиты в программу (`patches/api.mbox` через `include_str!`), её можно переносить одним exe.
- Каждый патч — письмо `git format-patch` с трейлером `Horizon-Forge-Api: <id>`. Программа
  читает `git log`, видит, какие id уже есть, и накладывает только остальные. Проверено:
  чистая копия → все этапы; копия с этапом N → только следующие; повторный запуск →
  «API уже стоит».
- **Применяется каждый коммит набора**, а не только помеченные: сопоставление по теме
  письма (`Subject`) с `git log`. Раньше брались лишь коммиты с трейлером, и правки,
  куски этапов и фиксы терялись. Проверено: установка на чистый базовый коммит даёт
  **побайтово то же дерево**, что моя ветка; обновление со старой 6-этапной установки
  ставит оставшиеся 22 коммита и снова даёт то же дерево.
- Работает в ветке `horizon-forge-api`, если она есть (недостающее считается по ней, а
  не по ветке, на которой стоит пользователь); при грязной рабочей копии отказывается.
- Нет имени пользователя в git → подставляется своё для коммита (иначе `git am` падает).
- Конфликт с более новой версией Horizon распознаётся отдельно от прочих ошибок git.

**Почему профиль `fast`.** У Horizon `release` = thin LTO + `codegen-units = 1`: 13 минут
сборки. `fast` = без LTO, 16 частей, инкрементально: первая сборка ~9,5 минуты, повторные
**2–2,5 минуты**, если менялся только код модов (замерено). Для игры разницы почти нет.

**Почему конвертер обёрнут вокруг `horizon-port-pack`.** В Horizon уже есть качественный
перенос контента (блоки по шаблонам, рецепты с апгрейдом форматов, лут, теги, генерация
мира) и чтение классов без декомпиляции (по суперклассам/методам/константам определяет:
block entity, меню, сущность, рендерер, Mixin...). Дублировать это было бы хуже; поверх
добавлен отчёт по этапам API.

| Проблема | Причина | Решение |
|---|---|---|
| Пример `beacons` вдруг потребовал capability `block-entities` | тип `block-entity` был объявлен в импортируемом интерфейсе, а экспорт его использовал — импорт тянулся во все моды | запись перенесена в экспортируемый интерфейс; импорт остаётся только у модов, вызывающих `get/set` |

| У пользователя ячейки «не сохранялись» | сеансы по 20–60 секунд: лодстоун не успевали поставить | проверка через `horizon-ctl` показала, что всё работает |

## 9. Текущие ограничения

- **Мультиблоки:** сравниваются только id блоков (не свойства), повороты — только на
  четверти, проверка раз в секунду, не на каждое изменение соседа.
- **Предметы:** нет левой руки, ломания блоков инструментом мода, эффектов при ношении,
  имени/подписи из данных; часть урона (мобы-мили, стрелы, PvP) не доходит до `player_hurt`
  (подробности — в `docs/mods.md`).
- **Рецепты:** изменённые файлы читаются при следующем запуске модов, теги раскрываются
  один раз при загрузке, `by_input` — по предметам.
- **Сеть:** сервер не знает, есть ли у клиента клиентская половина; экраны — только из
  виджетов `ui` (текст, кнопки, предметы, списки), без свободной вёрстки и текстур;
  половина в in-frame одиночной игре не поддерживается.
- **Меню:** вид — только сундук; в слотах инвентаря нет растягивания (drag), обмена
  цифрами и сбора двойным кликом (безопасно откатываются). Shift-перенос из инвентаря
  игрока в блок реализован, но в игре вручную не проверялся.
- **Воронки и ванильные блоки** не видят инвентари модов (нужен мост к ванильным
  контейнерам).
- **Блоки:** блок-сущность создаётся только при установке
  игроком или модом (не через `/setblock`, поршни, структуры).
- **Контент и логика — два мода** (контентный 0.2 + серверный 0.3).
- **Сущности:** только ванильные виды тела, урон не от игроков не доходит до хука, только
  измерение сервера, без своего ИИ (подробности — §5г).
- **Жидкости:** только баки на block entities (§5д): нет жидкостей в предметах, своих жидких
  блоков и видимости для ванильных воронок.
- **Редстоун:** см. §5е (нет визуального подключения провода, компараторов, quasi-connectivity).
- **Эффекты:** только ванильные частицы и звуки по имени (§5ж).
- **События игры:** только уведомления, без источника урона, дальних убийств, подбора предметов и отмены (§5з).
- **Дисплеи:** нет `item_display`, своих моделей кроме блоков и плавного следования модели за
  движущимся мобом (позиция пересоздаётся).
- **In-frame одиночная игра** (редкий режим без серверного потока) не поддерживает меню и
  дисплеи; обычная одиночная игра поддерживает.
- **Энергия:** лимит `max-receive` — на вызов; `push` может положить в одного соседа за
  два круга (терпимо, но не строгая модель FE).
- Часть кода писалась без запуска игры (ноутбук): я прогнал её тестами и вживую, но не
  всё (например, ×10 заряд ядра и «удар посохом» вручную не измерены).
- **Серверный мод не может нести контент** (блоки, предметы, `assets/`, `data/`): для этого
  нужен отдельный контентный мод 0.2 с тем же id (§10.3).
- **Нет межмодовых вызовов** (библиотечные моды вроде BrandonsCore), §10.5.
- **Нет страницы настроек** в «Настройки → Моды» для серверных модов; конфиг — файл и команды мода.
- **Нет телепорта игрока и принудительных действий над игроком** (Dislocator DE).
- **Конвертер не переводит логику Java**: перенос кода — ручной/ИИ поверх API; конвертер переносит
  контент и пишет отчёт.
- **Пилотного мода «в духе DE» ещё нет**: API проверялось одним примером `cells`, он покрывает все
  возможности, но не доказывает, что они сходятся в настоящей машине вроде реактора.
- Ветка **не отправлена** апстриму; патчи привязаны к базе `f66f66c` — на сильно новой
  версии Horizon может понадобиться перебазировать (`install-api` честно скажет «конфликт»).

## 10. План максимальной совместимости

Цель — чтобы **для любого технического/контентного Java-мода** существовал путь: контент
переносится автоматически, логика ложится на API, отчёт честно показывает, чего не хватает.
Полностью автоматического пути для произвольного Java-кода не будет никогда (Mixin'ы и
обращения во внутренности MC), но можно довести долю «механического» переноса до
большинства модов.

### 10.1 Как устроены Java-моды и что каждому классу нужно

| Тип мода (примеры) | Что в коде | Что нужно в Horizon | Сейчас |
|---|---|---|---|
| Контентные (декор, руды, еда) | регистрации блоков/предметов, JSON | контентный мод 0.2 | ✅ авто |
| Генерация мира (биомы, структуры на JSON) | datapack-данные | контент 0.2 + worldgen | ✅/🟡 авто для JSON |
| Технические (DE, Mekanism, Thermal, IE) | block entities, энергия, инвентари, жидкости, меню, рецепт-машины, мультиблоки, рендер | этапы 1–5 + инвентари, жидкости, рецепт-типы, мультиблоки, клиентский UI | 🟡 база есть |
| Магия (Ars, Botania) | предметы с логикой, сущности, частицы, рецепт-типы, книги | этапы 6–8 + частицы + книги | ❌ |
| Мобы (Alex's Mobs) | сущности, модели, ИИ, анимации | этап 7 + модели | ❌ |
| Оптимизация (Sodium, Lithium) | Mixin в рендер/логику | **не нужно** — Horizon сам по себе их замена | — |

### 10.4 Конвертер: путь от jar к рабочему моду

 ├─ 2. контент: блоки, предметы, рецепты, лут,    (есть: port-pack)

 ├─ 6. перевод логики класс за классом на Rust    (сделать: ИИ-агент + шаблоны SDK)
 ├─ 7. автотесты: TOML-сценарии из описаний       (сделать)

### 10.5 Библиотечные моды и межмодовые вызовы

У DE есть BrandonsCore; у сотен модов — Curios, GeckoLib, Patchouli и т. п. Нужен механизм,
при котором мод вызывает функции другого мода:
- Мод-библиотека экспортирует WIT-интерфейс (`horizon:lib-brandonscore/...`).
- Рантайм линкует импорт мода-потребителя к экспорту мода-библиотеки (component model
  это умеет: композиция компонентов) с проверкой версий.
- Альтернатива попроще — общая шина сообщений (байты по имени канала) между модами.
Тогда каждую популярную библиотеку переносят **один раз**, а все зависящие от неё моды
переносятся проще.

### 10.6 Настоящие GUI вместо сундуков

После сети (этап 8): серверный мод шлёт данные, **клиентский мод того же id** рисует экран
своими средствами (`ui`-виджеты, `render`-фигуры, текстуры из `assets/`). Текстуры GUI
Java-мода конвертер уже переносит как ассеты. Сундучное меню остаётся как запасной вариант
для ванильных клиентов.

### 10.7 Апстрим и поддержка

- Ветка расходится с Horizon, который меняется ежедневно. Правильно: **форк на GitHub** и
  **PR автору по одному этапу** (правила проекта: PR < ~500 строк, пометка «Opened by ...
  AI agent», capability `experimental`, тесты и `pr_ready.py`). Этапы 2–5 по размеру
  укладываются; этап 1 и 3 стоит разбить на 2 PR.
- Пока ветка своя — `horizon-forge` перед установкой проверяет базу и честно говорит о
  конфликте; для новой версии Horizon патчи перебазируются (`git rebase`), `api.mbox`
  перегенерируется.
- Собственные правила Horizon: код только по Minecraft 26.3 и публичной документации, не по
  коду других модов. Для апстрима переносы модов — только как отдельные пользовательские
  моды, не в движок.

### 10.8 Протокольный мост (вариант C, для будущего)

Когда будут сеть, сущности и инвентари, появится и третий путь для **контентных** Java-модов:
Horizon-клиент подключается к NeoForge-серверу, а конвертер даёт клиенту реестры и ассеты
мода (их и так переносит). Для модов, логика которых целиком серверная, а клиентская часть
— только ассеты, этого может хватить. Это отдельный большой проект; сейчас не начат.

### 10.9 Правовые рамки

- Код и ассеты Java-модов принадлежат авторам. Перенос «для себя» — серая зона, раздавать
  результат можно только с разрешения (конвертер пишет это в манифест и отчёт; поле лицензии
  читается из jar).
- Декомпилированный код хранится только локально.
- Для DE лучше «по мотивам»: свои текстуры и модели, своя реализация механик.

## 15. Как делался каждый этап

Один и тот же порядок (его же можно использовать для следующих этапов):

1. **WIT** (`crates/horizon-mod-sdk/wit/horizon.wit`): интерфейс функций, при необходимости
   интерфейс событий-экспортов и **отдельный host-мир** на каждый новый экспорт (иначе серверные
   моды, собранные до этапа, перестали бы грузиться: нет нужного экспорта).
2. **Capability**: `manifest.rs` (`ALL`, серверный ли, интерфейс, экспериментальный, описание для
   игрока, `Display`), `api_level.rs` (новые функции с новым уровнем; тест справочника требует, чтобы
   каждая функция была перечислена).
3. **Рантайм** (`runtime.rs`): `bindgen`-модуль мира, `Host` для `State`, `Output` (очередь «мод →
   игра»), поле в `Running`, инстанцирование экспорта при старте, методы `Mods`.
4. **Хранилище**, если нужно сохранение: рядом с block entities (`BlockEntities`), в своём файле в
   `data/horizon/`, «занимается» хуками вместе с ними (`lend`), удаляется вместе со своим блоком.
5. **Песочница** (`testing.rs`): шаги и проверки `expect.*` для новой возможности — чтобы сценарий
   проверял её без запуска игры.
6. **SDK** (`horizon-mod-sdk/src/lib.rs`): реэкспорты, методы-хуки `ServerMod`, построители,
   реализация экспорта в макросе.
7. **Пример `cells`** + TOML-сценарий + счётчик сценариев в `sandbox.rs`.
8. **Игра** (`horizon-client`): мост — приём `Output`, заём состояния на время вызовов, события.
9. **Документация** (`docs/mods.md` + регенерация `mods-reference.md`), тесты, clippy, быстрая сборка.
10. **Проверка в игре** (`horizon-ctl`): запуск, команда, чтение состояния; перезапуск, если есть
    сохранение.
11. **Коммит** с трейлером `Horizon-Forge-Api: <имя>-<n>`, `git format-patch` в `api.mbox`, пересборка
    `horizon-forge`, проверка «чистая установка даёт то же дерево».
12. **Отчёт и память** обновляются.

**Приёмы, повторявшиеся в разных этапах:**
- **«Заём»** (lend): игра на время вызова отдаёт рантайму мир, хранилище, сущности, инвентари
  игроков (потому что чанки или узел гостей «изъяты» из игры); после вызова возвращает и применяет
  очередь `Output`.
- **Состояния, которые нельзя вычислить внутри вызова, считает игра заранее** (входы редстоуна) и
  кладёт в заём; события получают сравнением состояния за тик (события игры, сущности).
- **Метки в сохранении** вместо отдельной базы (сущности: `Tags`), когда у данных уже есть
  ванильное хранилище.
- **Проверки в хосте только формы и границ**, всё, что знает только игра (есть ли такая частица,
  блок), — «отбросить и записать в лог».
- **Лимиты на вызов** у всего, что отправляется (эффекты, спавны, сообщения, записи конфига).
- **Одно место правки движка там, где без этого нельзя**: `LevelAccess::mod_signal` для редстоуна;
  остальное — снаружи, на уровне игры и рантайма.
- **Проверка вживую до коммита**: каждый этап искал ошибки, которых юнит-тесты не видят (гость и
  узел, двойной клик по рукам, самоблокировка ячеек, ключевые слова WIT).
